# M08 — Files: Upload Pipeline, Versions, File Codes, Cache, Handovers, Trail

**Depends on:** M05 (the queue and `ARCHIVE_FILE`), M07, M03.
**Produces:**

- the resumable browser-to-server upload;
- content-addressed blobs;
- file codes;
- versions and task links;
- the local cache with eviction;
- downloads (cache or OneDrive);
- handovers and the trail;
- the library;
- search.

**Failure IDs:**

- F-FL-1: upload interrupted.
- F-FL-2: hash mismatch at the end of an upload.
- F-FL-3: disk nearly full.
- F-FL-4: orphan remote file (owned by M05, wired here).
- F-FL-5: remote file missing (owned by M05, wired here).
- F-FL-6: evicted file requested while offline.
- F-FL-7: a new version is never a retry.
- F-FL-8: blocked file type.

## 1. File code

```
{YYYYMMDD}-{HHMMSS}_{EMPID}-{FirstnameL}_{TASKCODE|LIB}-{slug}_v{N}.{ext}
example: 20261109-154312_EMP003-RahulS_T-2026-000123-monthly-sales-report_v2.xlsx
```

- The time is the server's upload-commit time, in IST.
- `FirstnameL` is the first name, ASCII-folded, plus the last initial.
- `slug` is the task title, lowercase, ASCII-folded, `[a-z0-9-]` only, collapsed hyphens, at most 40 characters.
- `ext` is the original extension, lowercased; at most 10 characters, else `bin`.
- Allowed characters overall: `[A-Za-z0-9._-]`.
- Generated by `files.codes.make_code(...)`. Unique constraint; on the (rare) collision append `-2`.
- The original filename is kept in `original_filename`.

## 2. Upload pipeline (browser → server)

1. `POST /files/uploads` with `{idempotency_key, task_id?, file_id? (null = new file), assignment_id?, relation, original_filename, size, sha256}`.
    - The browser computes SHA-256 in a Web Worker before starting; this works for 200 MB.
    - The server validates:
        - permission (`file.upload` on the task or assignment);
        - `size ≤ OTS_UPLOAD_MAX_MB`;
        - extension not in the block list: `exe msi bat cmd ps1 vbs js jar scr lnk com` (F-FL-8; the Super Admin may override per upload, audited);
        - the disk admission check (F-FL-3): free space after reserving `size × 1.1` must stay ≥ 10% of the disk, else 507 "Server storage full", after first triggering cache eviction.
    - Creates `upload_sessions` (state RECEIVING) and returns `{upload_id, piece_size: 8388608, received_bytes}`.
    - The same key returns the existing session with its `received_bytes`, which is how resume works (F-FL-1).
2. `PUT /files/uploads/{id}` with `Content-Range: bytes a-b/total`.
    - The server appends to `/srv/data/staging/{id}.part` only if `a == received_bytes`. Otherwise it returns 416 with the current `received_bytes`.
    - Write in 1 MiB chunks, fsync on each piece, update `received_bytes` and `last_piece_at`.
3. On the last piece the server computes SHA-256 of the staged file.
    - A mismatch (F-FL-2): state REJECTED, delete the part file, return 422. No file record is created.
4. **Commit transaction:**
    1. Move the part file to `/srv/data/blobs/{sha[0:2]}/{sha[2:4]}/{sha}` with an atomic rename. If the blob already exists (same content), discard the staged copy and reuse it.
    2. Upsert `blobs` (`cached = true`; state STAGED, or keep ARCHIVED if the blob already existed and is archived).
    3. Create `files` (if new) and `file_versions`: `version_number = max + 1` under `SELECT … FOR UPDATE` on the files row; `file_code`; state STAGED; `idempotency_key` unique.
    4. `task_files` link.
    5. `task_events` `file.version_added`.
    6. Enqueue `storage_operations` `ARCHIVE_FILE`, unless the blob is already archived.
    7. Publish `file.staged`.
5. `ABANDONED`: the `files.staging_sweep` job deletes part files with no piece for 24 h and marks the session ABANDONED.
6. **F-FL-7:** a deliberate new version always uses a new idempotency key, so it becomes N+1. A retry of the same key never creates N+1.

## 3. Archive completion (handler for `ARCHIVE_FILE`)

`files.on_archived(op, ref)`, inside the finishing transaction:

- set the blob's `drive_id`, `item_id`, `etag`, `archived_at` and state ARCHIVED;
- set every `file_versions` row with that `blob_sha256` to ARCHIVED;
- append to the monthly manifest;
- publish `file.archived`. The UI drops the "Not yet off-site" badge live.

## 4. Cache (`/srv/data/blobs`)

- `files.cache_evict` runs at 02:45 and on demand when the cache is above 90% of `OTS_CACHE_CAP_GB`.
- It deletes local copies of **ARCHIVED** blobs only, least recently used (`last_accessed_at`) first, until the cache is at 80% of the cap. It sets `cached = false` and `local_path = null`.
- It never evicts STAGED, ARCHIVING, RETRY_WAIT, BLOCKED_*, FAILED, MISSING or DRIFTED blobs.
- Selfies are not in the cache.

## 5. Download

`GET /files/v/{version_id}/download`:

1. Permission `file.download`. The request audits `file.download` and writes `file_access_log`.
2. **Cache hit:** `FileResponse` streams the local blob. Set `last_accessed_at` (throttled to one write per hour per blob). `Content-Disposition: attachment; filename="<file_code>"`, plus `X-Content-Type-Options: nosniff`.
3. **Cache miss:**
    - If the storage queue is not blocked and Graph is reachable: stream from `provider.open_read` to the client while teeing to `staging/fetch-{sha}.part`. When it completes, verify SHA-256 and atomically move it into the cache. Set the source to `ONEDRIVE`.
    - If Graph is unreachable (F-FL-6): return a page "Archived: available when the internet returns", create a `notifications` subscription for the user, and enqueue a fetch job that caches the file and notifies them once done.
4. **Preview** (`/files/v/{id}/preview`): only PDF, PNG, JPG, WEBP and TXT. Served from a sandboxed response with `Content-Security-Policy: default-src 'none'; img-src 'self'; object-src 'self'; sandbox`.

## 6. Handovers and trail

- "Send file to…": choose recipients (permission: your manager, people on the same task, or anyone if you are a Sub-Admin or Super Admin) and a note. Creates `file_handovers` and recipient rows, publishes `file.handed_over`, and notifies each recipient.
- **First open:** the first download or preview by a recipient sets `first_opened_at` and publishes `file.handover_opened`.
- **Trail tab:** a timeline merging uploads and versions, handovers sent and opened, downloads (`file_access_log`), task-link events, `ARCHIVED` time and any MISSING/DRIFTED events.

## 7. Library and search

- **Library:** `library_folders` tree, with LIBRARY visibility for reference documents (Super Admin managed). An "Attach existing file" picker searches previous task files and the library; attaching creates a `task_files` row with `relation = REFERENCE` and copies nothing.
- **Search** (`/files/search`):
    - full text on `file_code`, `original_filename`, task title and uploader name;
    - filters: date range, uploader, task, extension, relation, state;
    - implemented with a `tsvector` on `file_versions` (generated) plus `pg_trgm` on `original_filename` and `file_code`;
    - scoped by permission;
    - target under 200 ms at 100k versions.
